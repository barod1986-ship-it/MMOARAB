# V1 Final Release Audit — REV14

Audit date: 2026-08-19

## Decision

V1 is **source-implementation complete but not release-ready yet**. REV14 closes the last source-side privacy gap found by this audit. Definition of Done still depends on real immutable production artifacts and evidence that cannot be truthfully manufactured in this source-only environment.

This audit also found and fixed a release-gate weakness: the earlier `check:controlled-release-ready` trusted state booleans and manifest fields too much. A fabricated manifest plus zero-byte lockfiles could therefore produce a false green result. The gate is now evidence-driven and fail-closed.

## Corrections implemented by this audit

1. `scripts/verify_controlled_release_ready.py` now validates the real release evidence rather than trusting booleans:
   - parses and structurally validates npm and uv locks;
   - re-hashes the extension ZIP, every Engine artifact and every compatibility sidecar;
   - verifies recorded byte counts;
   - inspects the exact extension ZIP and re-enforces Manifest V3, Chrome 148, required/optional permission, static-content-script and structured-clone constraints;
   - verifies `SHA256SUMS` exactly and rejects missing, extra, hash-mismatched, symlink or untracked directory/archive entries;
   - binds browser/Engine smoke records to the SHA-256 of the exact `controlled-release.json`;
   - requires production `default-v1` smoke evidence for V1 releases;
   - requires the V1 native target set (`windows-x86_64`, `macos-arm64`, `linux-x86_64`);
   - validates the production ML freeze instead of trusting `phase5bProductionFreezeReady`;
   - requires V1 SBOM/license metadata;
   - validates the frozen production profile/privacy descriptor and binds the Engine smoke fingerprint to it;
   - retains additional public Store/support/rollback gates for `public-v1`.
2. `scripts/prepare_controlled_release.py` now rejects symlink release inputs, unsafe artifact names, output filename collisions, permission/optional-host drift, forbidden packaged release content, and non-final compatibility metadata for `public-v1`. Compatibility metadata is bound to the bytes that were validated, and assembly is transactional: files are staged first and atomically promoted only after the complete archive is valid.
3. Source integrity is now complete rather than hand-maintained:
   - `scripts/source_integrity.py` defines the deterministic source set;
   - `scripts/update_source_sha256s.py` regenerates `SOURCE_SHA256SUMS.txt`;
   - `scripts/verify_source_integrity.py` rejects omitted, stale and hash-mismatched source entries.
   - This closes the discovered omission of `store/release/profile-privacy.json` and `store/release/store-candidate-contract.md`.
4. A regression suite in `tests/release-ready-gate-smoke.py` proves that missing archived bytes, empty/fabricated lockfiles, and a metadata-only remote-consent claim with tampered executable enforcement are rejected.
5. The controlled-release CI installs the pinned uv version, runs `uv lock --check`, verifies complete source integrity, and runs the release-gate regression suite before assembly.
6. Candidate workflow provenance is now checked before download: every selected Extension/Linux/Windows/macOS run must have succeeded, must come from its expected workflow, and must have the same `head_sha` as the controlled-release assembly commit. This prevents mixing artifacts from different source revisions.
7. A V1 controlled archive now carries the exact required release metadata (`extension.cyclonedx.json`, `engine.cyclonedx-1.5.json`, `engine.pylock.toml`, `MODEL_LICENSES.json`) under hash, and V1 assembly fails unless the complete Windows x86_64 + macOS arm64 + Linux x86_64 target set is present.

## Remaining blockers that must stay fail-closed

### Dependency/build reproducibility

- A genuine `package-lock.json` still needs to be generated by successful npm registry resolution and validated with `npm ci`.
- A genuine `engine/uv.lock` still needs to be generated with the project-pinned uv and validated with `uv lock --check`.
- No lockfile is hand-written or fabricated.

### Lock bootstrap and real qualification execution hardening added after the audit

The source now includes a centralized release toolchain policy and a manual `bootstrap-dependency-locks` workflow. It creates `package-lock.json` and `engine/uv.lock` only through real registry resolution with pinned Node/npm/Python/uv versions, validates clean installs/tests, regenerates `SOURCE_SHA256SUMS.txt`, and returns exact lock artifacts for review. It deliberately does not auto-commit or fabricate a lock when registry access is unavailable.

REV11 also closes the prepare/review/execute sequencing gap. The protected qualification workflow now generates real locks on a network runner, restores those exact bytes on the self-hosted runner, preflights the authorized corpus plus all reviews/manual LaMa/AOT packages before model download, acquires exactly seven automated artifacts, and seals one stable run plan. Benchmark execution is resumed later from that same workspace after a review is sealed to its exact `runPlanSha256`; no reacquisition/re-intake occurs between review and execution. Run plans and freezes are now bound to the exact npm/uv lock hashes.

### Production Engine / ML

- The legal production corpus, final human reviews and exact model/checkpoint/font bytes must still be supplied to the protected qualification runner; this source archive does not fabricate them.
- The REV11 execution path can now acquire/intake the seven automated artifacts and reviewed LaMa/AOT packages and can create the freeze, but a real `production-profile-freeze.json` remains a blocker until that workflow actually runs on the authorized corpus and the gate passes.
- Production detector/OCR/role/translation/inpainting runtime paths are now implemented, but `default-v1` remains fail-closed until the exact role revision and LaMa/AOT ONNX winner are proven by the legal corpus, artifact hashes/provenance, dependency locks and production freeze.
- The ML gate now consumes raw per-block SFX evidence, deterministically rebuilds the benchmark report, and requires exact correspondence with independently hashed corpus annotation block IDs before a freeze can be produced.
- The frozen production privacy descriptor/fingerprint must match that runnable profile. If it declares external transfer, its release metadata must name the provider(s) and assert the implemented versioned consent flow; the release verifier independently proves that executable Extension + Engine enforcement still exists.

### Native artifacts and metadata

- Final native artifacts are required for Windows x86_64, macOS arm64 and Linux x86_64.
- Required signing/notarization must be completed for the release class.
- Extension/Engine SBOM, pylock and model-license inventory must be generated from the final locked graph.
- Fresh-machine Engine smoke must be recorded against the exact controlled manifest SHA-256, using `default-v1` for V1.

### Browser acceptance

- The exact tested extension artifact must pass a fresh-unpacked Chrome 148 acceptance run.
- It must also pass the current Stable acceptance run recorded in `release-state.json` (Chrome 151 at this audit).
- Those smoke records must reference the exact controlled manifest SHA-256; toggling a state boolean is insufficient.

### Public V1 only

Public Chrome Web Store release additionally remains blocked until the Phase 8 publisher, listing, public URL, Store candidate, Store-installed smoke, production download, support-channel and rollback gates are satisfied with real evidence.

## Definition-of-Done interpretation

Phase 9 can be considered **implementation-complete**, but V1 is done only when `npm run check:controlled-release-ready` passes against real immutable artifacts and evidence. The release gate is now intentionally harder to satisfy than before; a green result should mean the referenced bytes, hashes, locks, smoke records, production profile and release metadata actually exist and agree.

## REV12 execution-attempt update

On 2026-08-19 the real qualification path was invoked as far as the available environment truthfully allowed. All local implementation gates passed (Engine 113/113, Phase 9 contracts 153/153, release-ready smoke 6/6), but the execution environment did not provide the pinned production toolchain, outbound registry/model network access, or operator-controlled production corpus/review/LaMa/AOT inputs. A prepare attempt using the shipped corpus template failed before acquisition because the template is deliberately unsealed. Therefore no `production-profile-freeze.json` exists and V1 remains not release-ready.

REV12 adds a diagnostic-only readiness probe so future protected-runner attempts can fail before consuming qualification time when toolchain/network/input prerequisites are visibly incomplete. The probe is not release evidence and cannot create or approve production evidence.


## REV13 sealed-input update

REV13 closes a remaining operational ambiguity in the first real qualification run. Prepare previously accepted the corpus, artifact-review directory and manual LaMa/AOT directory as separate workflow inputs. Although each was individually validated, that interface did not provide one durable operator-input identity before lock bootstrap and model acquisition.

The new sealed qualification input bundle content-binds the corpus manifest, every active artifact review, both reviewed manual packages, the exact seven-automated + two-manual topology, and all active qualification control policy files. The protected runner now performs a strict toolchain/network/semantic bundle preflight before the hosted lock bootstrap is allowed to start, and prepare verifies the same bundle again before downloads. Engine regression coverage is now 120/120 and Phase 9 contracts 164/164.

This still does **not** satisfy the V1 release blocker: the real authorized corpus, final human review records, reviewed LaMa/AOT package bytes, seven acquired automated artifacts, passing benchmark evidence and lock-bound `production-profile-freeze.json` must still exist on the protected qualification infrastructure. REV13 makes that handoff deterministic; it does not replace those external facts.


## REV14 final source-side closure

The REV14 audit discovered a genuine remaining implementation blocker rather than an external evidence gap: the frozen production translator architecture permits extracted dialogue/narration OCR text to leave the device, but the shipped product had only a local-processing first-run consent. The release verifier could also have trusted a future `remoteTransferConsentImplemented=true` descriptor without proving executable enforcement.

REV14 fixes both issues:

- a separate consent record is versioned as `2026-08-19.remote-transfer.v1` and is content-bound to `profileId`, `profileFingerprint`, the complete privacy descriptor, the exact provider list, and acceptance time;
- the Side Panel presents the second disclosure only after local consent and only for a current `ready` profile that declares external transfer;
- the Extension gateway force-refreshes capabilities and refuses both create and start/resume without a matching proof;
- the Engine independently re-verifies the proof on both `/v1/jobs` and `/v1/jobs/{ticket}/start`, preventing UI/storage bypass from authorizing remote transfer;
- profile capabilities explicitly name external providers (`OpenAI` only when the frozen supported text-only production translation path actually leaves the device);
- the controlled-release verifier invokes `scripts/verify_remote_transfer_consent_contract.py` and therefore cannot accept a release-metadata claim when the executable gate is absent;
- regression coverage deliberately tampers with the Extension enforcement and proves the claim is rejected.

After this correction, the source-side runtime adapters and remote-transfer consent implementation are complete. The remaining V1 blockers are evidence/production-operation gates: genuine npm/uv locks; the authorized sealed qualification bundle; exact seven automated artifacts plus reviewed LaMa/AOT packages; a passing real corpus benchmark and lock-bound `production-profile-freeze.json`; frozen release privacy/provider metadata; final native artifacts/signing/notarization; SBOM/license metadata; fresh Chrome 148/current-Stable and Engine artifact smoke; and, for public V1, Store/publisher/support/download/rollback evidence. No substitute evidence is generated by REV14.


## REV16 — qualified-evidence promotion closure

REV16 closes the previously missing transition from a passing protected qualification into the release source tree. The production freeze is now source-bound (`production-profile-freeze-v4-source-and-release-evidence-bound`) to the exact benchmark run plan, executor source and qualified Extension/Engine runtime trees. A passing execute run exports the genuine npm/uv locks plus the freeze and safe control summaries as one content-addressed release-evidence artifact. A separate protected promotion workflow accepts only a successful execute run from the same source commit, revalidates every lock/freeze/source binding, allows only the evidence paths to change, and opens a review PR rather than pushing to the release branch.

This removes a source-side handoff blocker but still does not claim the external evidence exists. Real qualification inputs/network/runner execution, the first passing freeze, controlled native/Extension artifacts, profile/privacy descriptor, and exact-byte browser/native smoke remain required.


## REV17 — exact artifact smoke evidence closure

REV17 closes the source-side path from an immutable controlled archive to auditable native/browser acceptance evidence without inventing any smoke result. `controlled-release.json` is schema v2 and source-bound; V1 archives also carry the exact promoted production freeze. Native smoke runs the archived bytes on protected Linux x86_64, macOS arm64 and Windows x86_64 runners, re-hashes the qualified model/font bytes and qualified source binding, performs a real production translation, and emits only the resulting observation JSON. Public macOS `.pkg` evidence now requires a real clean system install after signature, stapling and Gatekeeper checks; extraction alone is not accepted as installation evidence.

A single production profile fingerprint is no longer assumed across operating systems. The fingerprint intentionally covers runtime/codec identity, so Linux/macOS/Windows may legitimately differ. `store/release/profile-privacy.json` schema v2 therefore stores `profileFingerprintsByTarget`, while the privacy descriptor and exact external-provider list must be identical across all native observations. This preserves the runtime-bound remote-transfer consent contract on each client without making cross-platform V1 impossible.

Chrome 148 and current-Stable evidence is recorded from a real clean temporary Chrome profile using the exact controlled Extension ZIP and a specifically identified controlled Engine artifact. The browser recorder is intentionally interactive: the tool proves browser version, clean profile and artifact hashes, while the operator explicitly attests install, activation/consent, translated-fixture/SFX preservation and restore. The resulting observations, together with all three native observations, are promoted transactionally; a validation failure leaves all three source evidence mirrors unchanged.

No native or browser smoke record is pre-populated by REV17. The release remains fail-closed until these exact external runs are performed.

## REV18 V1 evidence orchestration addendum

REV18 found two release-path defects that were not visible while V1 evidence remained absent.

First, REV16/17 used one `sourceHeadSha` for both the benchmark-qualified runtime commit and the later controlled-artifact assembly commit. That cannot be true after the reviewed qualification-evidence PR is merged: the PR necessarily creates a later commit even when `src` and `engine/mte_engine` remain byte-identical to the qualified runtime trees. The controlled manifest now carries both `qualifiedSourceHeadSha` and assembly `sourceHeadSha`. The production freeze remains authoritative for runtime-tree hashes, so this does not permit runtime drift.

Second, REV17 smoke promotion changed source-tracked release evidence without updating `SOURCE_SHA256SUMS.txt`. REV18 makes profile/privacy, smoke records, release state, the evidence-promoted orchestration checkpoint, and source-integrity checksum state one rollback-capable promotion transaction.

A six-stage content-addressed orchestration chain now prevents out-of-order V1 evidence use: qualification-promoted → controlled-assembled → native-smoke-complete → browser-smoke-complete → evidence-promoted → release-ready. The final private/public V1 gate requires the `evidence-promoted` checkpoint and independently re-hashes the referenced controlled manifest, production freeze, profile/privacy, smoke records, and release-state bytes.

The REV18 private-V1 dry audit remains intentionally red with 19 evidence blockers. The additional blocker is the missing real orchestration checkpoint; no checkpoint is pre-populated or fabricated. See `docs/REV18_V1_EVIDENCE_ORCHESTRATION.md`.

## REV19 public Store/finalization addendum

A Real V1 orchestration audit found that REV18 could close private-V1 ordering but not a truthful public-V1 lifecycle. `evidence-promoted` locked the exact smoke/release-state bytes before Store submission, while `public-v1` required those same files to change later for Store-installed smoke and public rollout evidence. The old Store candidate workflow also rebuilt the extension ZIP from source, breaking the exact-byte controlled-artifact chain.

REV19 fixes both conditions. Public V1 now uses `evidence-promoted` as the immutable **pre-Store** checkpoint, a sealed `store-submission-handoff.json` to authorize only the exact controlled Extension ZIP, two Store-installed observations (Chrome 148 + audited Stable), then a second transactional `public-evidence-promoted` checkpoint. The final public gate requires the second checkpoint and re-hashes the Store candidate metadata/handoff as well as tracked post-Store evidence. A dedicated finalization workflow can emit an attested `release-ready.json` only after that final gate is actually green. No external evidence is synthesized.

## REV20 delivery/provenance audit addendum

The final V1 deliverable is now the verified `release/final/<release-id>/` capsule, not the orchestration checkpoint alone. A release-ready capsule must preserve exact controlled artifact hashes, carry the dependency locks/freeze and promoted evidence that produced the final gate, bind qualified/assembly/finalization source identities, and pass `scripts/final_release_capsule.py verify` before upload. `CAPSULE_SHA256SUMS.txt` is used to attest all capsule subjects, and the checksum index is separately attested.

A private-V1 finalization bug discovered during this audit was corrected: private `release-ready` sessions are no longer rejected by the public-only post-Store session validation branch.

## REV21 production-execution readiness audit addendum

REV20 closed final artifact delivery, but a production-operations audit found two remaining executable deployment defects before a real public run could start reliably.

First, protected self-hosted infrastructure requirements were distributed across workflows without one machine-readable contract. REV21 adds `release-control/production-execution-contract.json`, a source/workflow drift checker, live fail-closed runner probes and a dedicated readiness workflow. The contract covers the qualification Linux x86_64 runner plus Linux x86_64, macOS arm64 and Windows x86_64 release-smoke roles, including protected environments, required paths/secrets and exact canonical toolchain checks.

Second, the public signing workflows assumed credentials or helper paths pre-existed on ephemeral GitHub-hosted runners. REV21 removes that assumption. The macOS workflow imports protected Developer ID PKCS#12 identities into a temporary keychain and passes a materialized team App Store Connect API key directly to `notarytool`; cleanup removes all temporary material. The Windows workflow uses Microsoft Artifact Signing through OIDC and verifies every signed PE file independently before producing the signed ZIP. No signing credential is included in diagnostic/readiness reports.

This closes the source-side production bootstrap gap, not the external execution gap. A real protected runner fleet and environment configuration, authorized sealed corpus/reviews/LaMa/AOT bytes, network access, Apple/Microsoft signing setup and all 19/28 real private/public release evidence requirements are still required before V1 can be declared release-ready.



## REV22 GitHub infrastructure audit / first-real-run handoff addendum

REV21 could only validate a self-hosted role after GitHub had already scheduled the job. REV22 adds a separate repository-administration audit before those jobs. Using the versioned GitHub REST API, `scripts/audit_github_production_infrastructure.py` checks that all contract environments exist, each of the four production roles has an online runner with the complete required label set, and required environment variable/secret names are configured. Secret values are never requested or written to the report. Required-reviewer and prevent-self-review settings remain warnings unless explicitly promoted to blocking policy because their availability depends on repository visibility/plan.

The unified readiness workflow now gates all live runner probes on that GitHub-side audit. `release-control/production-execution-contract.json` also records the canonical first-real-run sequence and requires resume to preserve workflow run identities rather than rebuilding a stage opportunistically. This still does not provision the external infrastructure or create any release evidence; the actual project repository must expose a read-only administration audit credential and the real runner/environment configuration before the readiness workflow can become green.


## REV23 repository infrastructure pagination / resume audit addendum

A post-REV22 audit found that GitHub infrastructure discovery was first-page-only and that the `production-qualification-promotion` environment was used by a workflow but absent from the audited environment set. REV23 uses complete pagination for runners, environments, environment variables and environment secret-name collections, audits the promotion environment, and records the GitHub fine-grained permissions actually required by those endpoints.

REV23 also adds an operator-only first-real-run ledger. It cannot satisfy any release gate; it exists only to preserve run identities and manual review boundaries across a multi-stage production execution. Automated stages enforce minimum recorded workflow run IDs, while the existing workflows remain authoritative for provenance validation.

## REV24 repository provisioning closure

REV24 adds the missing repository-side provisioning handoff. The GitHub infrastructure audit is no longer merely diagnostic: `scripts/provision_github_production_infrastructure.py` can generate a contract-bound external config, create only missing deployment environments, materialize required environment variables/secrets from local operator environment variables, add the required custom labels to already-registered self-hosted runners, and re-run the live audit. Existing environment protection rules are deliberately preserved rather than overwritten. Runner registration is emitted as a host-local command that requests a short-lived repository registration token at execution time and never stores that token in the bootstrap config. This tooling does not create release evidence and therefore does not reduce the private/public V1 blockers until the real infrastructure and subsequent workflows actually run.


## REV25 repository onboarding identity closure

A post-REV24 audit found two operator-boundary risks: a bootstrap config was content-addressed but not bound to GitHub's immutable repository identity/default-branch head, and generated runner-registration commands interpolated repository/runner strings without a conservative shell-safety contract. REV25 requires an explicit `bind` step before all live mutation, seals repository ID/default branch/head plus workflow/source-integrity hashes, rejects local-origin/HEAD disagreement, quotes generated Bash/PowerShell arguments, and rechecks repository/head drift before runner registration. The first-real-run ledger inherits this binding. No V1 evidence blocker is closed merely by this onboarding layer.

REV25 also fixes a concrete REV24 operator-flow bug: changing placeholder runner names by manually editing the sealed bootstrap JSON invalidated `configSha256`, making the subsequent bind/apply path self-defeating. Runner mappings now use a dedicated `set-runner` command that validates the name and reseals the configuration after every change.


## REV26 production workflow trust boundary

A post-REV25 audit found that repository identity binding alone did not externally restrict production environment jobs to the bound default branch, and the read-only GitHub infrastructure audit token was still a repository-level workflow secret rather than an environment-scoped credential. REV26 moves `MTE_INFRA_AUDIT_TOKEN` to the dedicated `production-infrastructure-audit` environment and makes exact default-branch deployment policy a blocking requirement for every production environment. The live audit enumerates custom deployment branch policies and rejects protected-branches/allow-all/extra-policy configurations. New environments are provisioned default-branch-only; incompatible existing environments fail closed rather than being silently rewritten. REV26 also corrects `MTE_INFRA_PROVISION_TOKEN` requirements to include the `Actions:read` and `Contents:read` permissions consumed by live environment discovery and default-branch commit binding. This closes no V1 evidence blocker by itself.


## REV27 production run provenance closure

A post-REV26 audit found two remaining operator-flow ambiguities. Production environments restricted branch access but did not independently authorize the dispatching actor, and the resume ledger treated an evidence-promotion workflow that opens a PR as if its new evidence commit had already become the source for later builds. REV27 provisions a stable GitHub actor-ID allowlist and requires every production job to satisfy workflow-dispatch/default-branch/actor-ID guards. The ledger now records PR creation and reviewed merge separately, verifies merge-parent/source continuity plus changed-path allowlists, and advances the build source only after the merge. The public-V1 plan also includes the Store/post-Store evidence transitions before finalization. These controls improve execution provenance only; the existing real-evidence blockers remain fail-closed.

## REV28 launch/resume audit

The first-real-run path now has launch provenance as well as post-hoc run provenance. Automated stages are controller-dispatched from the ledger's exact default-branch commit and bound to a random run-intent nonce recorded before dispatch. GitHub run IDs returned by dispatch are persisted immediately; nonce-based recovery covers an interrupted local handoff without opportunistic redispatch. Automated success cannot be committed if the run title lacks the nonce, the actor ID is outside the sealed allowlist, the source/default branch differs, or the run did not conclude successfully. Failed pending launches require explicit retry and retain their old run identities. This is operational hardening only and does not reduce any real V1 evidence blocker by itself.

## REV29 manual-boundary audit addendum

The first-run audit found one remaining provenance asymmetry: automated jobs and PR transitions were identity-bound, but benchmark/Chrome human boundaries could still be represented by a boolean `manualReviewed`. REV29 makes those boundaries content-addressed and evidence-bound. Benchmark checkpoints bind the exact ready run plan and sealed review. Pre-Store browser checkpoints bind the exact controlled manifest, native-smoke orchestration session and the two Chrome observations. Public Store checkpoints additionally re-hash the exact Store candidate ZIP and bind its handoff/metadata plus the two Store-installed observations. Creation and recording both verify the authorized GitHub actor and the unchanged repository/default-branch cursor. These checkpoints remain operational handoff state rather than release evidence, so the real V1 blockers remain fail-closed.

REV29 verification keeps the release fail-closed: private-v1 reports 19 blockers and public-v1 reports 28 blockers. Manual checkpoints add operational provenance only and cannot satisfy those blockers by themselves.

## REV30 evidence source-transition audit addendum

The audit found that an evidence promotion could previously be recorded locally before a PR existed, and merged-PR verification did not cryptographically pin the review boundary to the exact PR head recorded at creation. REV30 adds explicit PR-created stages and a sealed `pendingEvidencePr` recovery plan. Every local promoted file is hashed before remote mutation and re-downloaded from the PR head for byte comparison. Merge progression is accepted only for the recorded PR number/head SHA and only when its merge commit is the current default-branch HEAD. This changes operational provenance only; it does not create qualification, smoke, Store, signing or release evidence and therefore does not satisfy any V1 release blocker by itself.

## REV31 local checkout provenance addendum

REV30 proved the identity of the merged evidence PR but did not prove that the operator checkout used by later local promotion had actually moved to that merge commit. REV31 adds mandatory post-merge checkout reconciliation after all three evidence source transitions. Any staged change, unrelated dirty source path, origin mismatch, stale local HEAD, or dirty reviewed file whose bytes differ from the exact merge blob fails closed before checkout mutation. Operational `release/` material is preserved and Source Integrity is re-run after reconciliation. This closes an execution-provenance gap only and does not reduce the V1 evidence blockers by itself.

## REV32 Actions-artifact retention addendum

The release audit now treats GitHub Actions artifact retention as an availability property rather than durable release evidence. Every automated first-run stage must seal its run metadata and uploaded artifact ZIP bytes into the local recovery chain before its ledger record is committed; manual review boundaries archive the exact reviewed evidence files as well. Missing, expired, digest-mismatched or subsequently tampered recovery material blocks continuation. The recovery bundle is explicitly operational and cannot satisfy qualification, smoke, signing, Store or final-release evidence gates by itself.

## REV33 recovery restore / rehydration addendum

Disaster recovery is now tested in the reverse direction as well as export. A valid recovery bundle can be activated on a clean checkout only when repository origin, default branch, exact source cursor, contract bytes, production workflow-set and Source Integrity match the sealed operational ledger. Activation is a single-directory atomic rename under `release/rehydrated/`; no source bytes are restored or `git clean`ed. The rehydrated ledger preserves the original stage/source/run semantics and changes only local recovery paths before resealing. Controller planning succeeds after the source bundle is removed, while tampered recovery bytes, a substituted repository origin or a changed checkout source cursor fail closed. Restore provenance is not release evidence and cannot satisfy any V1 release blocker.

## REV34 recovery rotation / off-site durability audit

REV34 closes the single-copy disaster-recovery durability gap above REV33 rehydration. Recovery rotation requires at least two exact bundle copies on distinct non-overlapping storage identities, at least one operator-declared off-site destination, HMAC-SHA256 authenticated copy receipts/state, and a real REV33 restore + `verify-restored` probe from a copied bundle before the new generation becomes active. Safe pruning is dry-run by default and preserves at least two complete generations. The tooling explicitly does not claim to prove physical geography of mounted storage and does not convert backup durability into release evidence.

Private/public V1 dry gates remain blocked by 19/28 real-evidence requirements respectively.
